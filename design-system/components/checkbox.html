Verifi Design System/Components/Checkbox

Checkbox

An independent yes or no. Several can be true at once, and the change applies when the form is saved, not the moment it is clicked.

Solid12 variantsFigma 30515:78521 ↗
Use this component in prototypes rather than drawing a checkbox. Verifi Design’s note: the label is a toggle on the component, so you switch it off where you do not want one and edit it in one place where you do, instead of retyping it in every layout. It also carries light and dark with it, so a prototype switched to dark mode brings the checkbox along without any manual recolouring. The same instance is what the table row selector uses.
One size: a 16px box inside a 24px target. checkbox/width and checkbox/height are 24; checkbox/padding is 4; 24 less 4 a side leaves the 16 × 16 box. Trinity names that outer frame touchpoint, and it is what WCAG 2.2 2.5.8 Target Size (Minimum), AA measures. Draw the box at 16 and give it 24 of room. Never scale the box to fill the target.

Behaviour

A checkbox waits. Clicking it stages a change that something else — Save, Apply, Done — commits. That single sentence settles most of the questions below, because a control that has not committed yet is allowed to be wrong, reversible, and quiet about it.

Checkbox or toggle? If flipping it changes the system immediately, with nothing to press afterwards, it is a toggle. A toggle inside a form with a Save button is a checkbox wearing a costume.
Checkbox or radio? If exactly one option may be true, it is a radio group. A single checkbox is also correct for one opt-in confirmation.

The indeterminate contract

Indeterminate is a readout, not a choice. A parent enters it because some but not all of its children are checked; nobody ever clicks a box into it. Get that backwards and you end up with a three-position control nobody can predict.

None checkedUncheckedChecks all children
Some checkedIndeterminateChecks all children
All checkedCheckedUnchecks all children

Try it

Real <input> elements, so indeterminate is the DOM property and the announcement is the browser’s, not a drawing of one. Tick children off one at a time and watch the parent fall into the dash. Then click the parent while it is dashed.

The line underneath reports the parent’s real state and what a click would do next.

From indeterminate, a click always checks all. It never unchecks, and it never cycles back to the partial state. Users reach for a parent checkbox to finish selecting, not to undo a selection they are halfway through — and undo is one more click away in either direction. A parent that cycled through all three states would make a two-item list take three clicks to clear.
  • Only a parent of a visible set may be indeterminate. A standalone checkbox has two states.
  • The parent reflects its children the instant they change. It is never stale.
  • Put the count in the label — All plants (3 of 7). The dash says partial; only the number says how partial.
  • Nesting stops at one level here. A parent of parents is a tree, and a tree needs disclosure, not checkboxes.

Select all, in a table that scrolls

The header checkbox in a long table is the one place this component routinely lies. “All” means the rows a person can see; the database means every row that matches. On a fleet list that is the difference between forty trucks and four thousand.

  • The header checkbox selects the loaded rows only, and it reflects those rows only. This is the default and it needs no explanation.
  • When the filter matches more than is loaded, offer the wider selection as an explicit second step, in words: 40 selected. Select all 4,182 matching? Never make the header checkbox silently mean the larger set.
  • Say what is selected, always, near the action that will act on it. A count is the cheapest protection against a destructive mistake.
  • Changing a filter clears the selection. Carrying a selection across a filter change is how people delete rows they never saw.
  • Selection survives sorting and pagination within the same filter. Sorting does not change which rows matched.

The header never means more than the rows you can see. The wider selection has to be asked for, in words.

Shift-click selects a range. Click one row, shift-click another, and everything between them takes the state of the row you clicked first. It is unadvertised and everyone who needs it already tries it. It must never be the only way to do something.
Handle the range on the row, not on the checkbox. When Shift is held, the browser suppresses a <label>’s activation behaviour entirely — it reads the gesture as a text-range selection, so the <input> never receives a click and never toggles. A listener on the input alone does nothing at all, silently. Bind the handler to the row, read shiftKey there, call preventDefault() and set the range yourself. The demo above does exactly this; it did not work until it did.

Required groups, and the error state Trinity does not draw

“Pick at least one” is a property of the group, not of any box in it, so the error belongs to the group too. Trinity has no error variant for the checkbox, and it does not need one: nothing about the individual box changes.

  • The message sits under the group, once, tied to the <fieldset> with aria-describedby. Not once per checkbox.
  • No box turns red. Reddening six boxes to say “one of these is required” tells the user nothing about which one, because the answer is none of them.
  • Validate on submit, not on blur. A group cannot be judged until the user has finished with all of it.
  • A single required checkbox — accepting terms — is the exception: the message sits under that one box, and the box may carry the --error border.

Disabled, read-only, or just absent

Three different situations that all get solved with disabled by reflex, and only one of them should be.

SituationUseWhy
The user could change this, but not yet — something else has to happen firstDisabled, with the reason in text nearbyDisabled with no explanation is the single most common complaint about any form. The state is honest; the silence is not.
The value matters but this user may never change itRead-only — render the value as text, not as a dead controlA checkbox the user cannot ever operate is a control that lies about being a control.
The option does not apply to this user at allLeave it outA permanently greyed row is visual debt on every screen after it.
Disabled does not mean unreadable. The value stays visible — a disabled checked box still shows its tick. Hiding the value because the control is inert loses the information as well as the control.

When the save fails

The checkbox commits with the form, so it has no loading state and does not need one. What it does need is a rule for the moment the form comes back.

  • On failure the boxes keep what the user set. Never silently revert — the user has to be able to press Save again without re-answering.
  • The failure is announced once, at the form level, in a toast or an inline message. Not on the checkbox.
  • If one box in a batch failed and the rest went through, say which. A partial failure reported as a total failure makes people redo work that already succeeded.

Touch

  • The 24 × 24 touchpoint is the AA minimum, not a comfortable target. Stacked checkboxes get 10px between them, which puts 34px between centres.
  • The whole label is part of the target. That is what makes a 16px box usable on a phone, so never render the label outside the <label>.
  • Two adjacent targets must not touch. Where a checkbox sits beside another control in a dense table row, give it its own cell.

Defaults

  • Default to unchecked unless checked is both the common choice and the safe one.
  • Never pre-check anything that consents on the user’s behalf. That is the one place a default is not a convenience.
  • A pre-checked box must survive a reset to the same value. If Reset clears it, it was never a default.

Settled by design

Four things about this component look like oversights and are not. They have been confirmed correct as drawn, so do not re-log them.

Looks likeActually
The tick vector is named Icon / Check / Temp.That is the final tick, not a placeholder. The name is historical.
checkbox/hover-stroke and checkbox/focus-inner-stroke hold the same value in both modes without being aliased.Deliberate. They are separate decisions that happen to agree today, and they are free to diverge without dragging the other with them.
Disabled drops the border entirely, so an unchecked disabled box is a solid grey square.Deliberate. Disabled is not meant to invite a second look — the grey block reads as inert faster than a greyed outline does.
checkbox/large/track/width and .../height sit in the checkbox namespace.Correct where they are. There is still one checkbox size; these are not evidence of a second.

Guidelines

Do

  • Write the label as the positive statement — what is true when it is ticked.
  • Put the parent checkbox above its children, indented away from them, and let it reflect them honestly.
  • Keep groups vertical, one per line. Horizontal rows force the eye to re-find the box after every label.
  • Give the group a <legend> that states the question, even when it looks redundant next to a heading.
  • Say what a selection contains before offering an action on it.

Do not

  • Do not write a negative label. “Do not show returned concrete” makes an unticked box a double negative.
  • Do not use a checkbox for something that takes effect immediately — that is a toggle.
  • Do not put more than about seven in one ungrouped list. Past that, group them or move to a filtered list.
  • Do not let a click set a box to indeterminate. It is a readout of children, never a choice.
  • Do not disable a checkbox without saying why somewhere the user can see.

Accessibility

  • Use a real <input type="checkbox"> inside a <label>. Do not rebuild it from divs. Everything below comes free if you do, and has to be hand-built and maintained if you do not.
  • Set indeterminate in JavaScript — it is a property, not an attribute, and it cannot be expressed in HTML alone. It also does not change checked, so send the parent’s real value, not the dash, to the server.
  • A native indeterminate checkbox already reports aria-checked="mixed". Do not also set the attribute by hand — the two can disagree.
  • Group related checkboxes in a <fieldset> with a <legend>. That is what makes a screen reader announce “Plants, 3 of 7” instead of six unrelated checkboxes.
  • Space is the activation key. Enter must not submit from a focused checkbox.
  • The visible label is the accessible name. Do not add a different aria-label — speech users say what they see.
  • A group error is tied to the <fieldset> with aria-describedby and announced once, in a live region. Six identical errors is six interruptions.
  • Shift-click range selection needs a keyboard equivalent. Shift plus arrow, or nothing — never a mouse-only path to a bulk action.
  • In a table, the header checkbox needs its own accessible name (Select all rows). An unlabelled checkbox in a <th> reads as nothing at all.
Target size passes at AA, not AAA. The 24 × 24 touchpoint meets 2.5.8 Target Size (Minimum), AA exactly. 2.5.5 Target Size (Enhanced) asks for 44 × 44 and is AAA, which this system does not target. The clickable label carries the real target well past 44px in practice. See Accessibility.
Disabled is exempt from contrast, not compliant with it. The disabled fill measures 1.94:1 and the disabled label 2.14:1. WCAG exempts inactive controls from 1.4.3 and 1.4.11, so these are not failures — but do not cite them as passes either, and do not put information in a disabled control that the user needs to read.
